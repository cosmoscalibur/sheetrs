# Fidelity: LibreOffice's behavior, and where it differs from Excel

The engine behaves as **LibreOffice 26.8** does. There is no behavior to choose: Excel
compatibility is whatever LibreOffice itself provides, and a workbook that expects Excel's
answer where the two differ gets LibreOffice's, reported here. What varies from one file to
another is not a mode but what the file carries and how its functions are named:

| Decided by | What |
| ---------- | ---- |
| The file's **format** | How it is read: the settings the document stores (iteration, search criteria, case sensitivity, null date, the syntax `INDIRECT` reads), the syntax of defined names, the reading of a bare `#REF!`. |
| The function's **namespace** | Which function a name is, where the same text names two (`CEILING`, `FLOOR`, …): `core` (the OpenDocument standard, no prefix), `microsoft`, `libreoffice`, `openoffice`, `legacy`; see *Format and namespace*. |
| The build configuration (`[locale]`, `--locale`) | Application-wide regional settings (separators, date order, month and day names, boolean names, currency). Fixed at build time. |
| The run | Only the clock (`NOW()`) and the random seed. |

The tables below say where that behavior differs from Excel's. The Excel column is Excel's
**documented** behavior, not an Excel run: no Excel is available here, which makes it the
part to re-verify against real Excel files when possible.

How the engine implements a difference: in the operator or coercion code (`^`, `<`, `&`, text
conversion), as a function that behaves as a whole in LibreOffice's way (`ISNUMBER`), in the
date system (the document's null date), or in a document setting the file carries.

Evidence: `scripts/probe_behavior.py` writes the probe formulas; LibreOffice 26.8 recalculates
them into `tests/assets/probe.ods`; `tests/semantics/probe.rs` requires the engine to reproduce every
one (except the listed gaps) and pins the answers that differ from Excel's.

## Format and namespace

Question: does LibreOffice run an XLSX in an "Excel compatibility mode" and an ODS in its own? `scripts/compare_formats.py` answers it with
LibreOffice 26.8 on the oracle formulas (`semantics.xlsx`) and the probes
(`probe_behavior.py`): **X** is the XLSX recalculated in full, **O** the same formulas typed into a
document created in LibreOffice (an ODS with ODF's defaults), **O2** O with X's document settings
copied, **R** X saved as ODS, reloaded and recalculated.

| Comparison | Formulas that differ |
| ---------- | -------------------- |
| X vs R (XLSX → ODS round trip) | a bare `#REF!` (below); no probe |
| X vs O (native ODS) | the ones of O2 and the differences of the document settings, below |
| X vs O2 (native ODS, X's settings) | all explained below; no probe |

The same function gives the same result in both formats: `0^0`, booleans, `SUM("1")`, text-to-number
conversion, date serials, `TEXT`, regular-expression and wildcard criteria, errors. There is no
Excel mode. What differs is **document state** and **names**:

| Difference | XLSX import | Native ODS | Where it lives |
| ---------- | ----------- | ---------- | -------------- |
| Case-sensitive comparisons (`"a"="A"`) | no (`IgnoreCase`) | yes | `table:case-sensitive`; the engine reads it (`Search`) |
| Wildcards / regular expressions | wildcards | wildcards (a new document); the ODF default when the attribute is absent is regular expressions | `table:use-wildcards`, `table:use-regular-expressions` |
| `INDIRECT` and `ADDRESS` text syntax | Excel A1: `Sheet!A1`; `Sheet.A1` is `#REF!` | Calc A1: `Sheet.A1`; `Sheet!A1` is `#REF!` | `settings.xml` `SyntaxStringRef` (2 = Excel A1; absent = Calc A1). The engine reads it (`string_ref_excel`) and applies it to a constant `INDIRECT` at build time too |
| Bare `#REF!` typed in a formula | unknown name (`#NAME?`) | `#REF!` | the XLSX import (`Model.from_xlsx`) |
| `CEILING`, `FLOOR` | Excel's (`CEILING.XCL`) | LibreOffice's own: signs must agree (`Err:502` otherwise), mode flips rounding of negatives | **function namespace** (below) |
| Iteration, null date, two-digit-year window | from `calcPr` | from `table:iteration`, `table:null-date`, `table:null-year` | already read from each file |
| `SUBTOTAL`/`AGGREGATE` over hidden rows | hidden rows of the file | same | rows are read from the file |

(O differs from X also on `SUBTOTAL`/`AGGREGATE` and `INDIRECT`, which are artifacts of how O was built: it has no hidden
rows, and `Sheet!A1` is not Calc syntax.)

So the behavior is **not** a function of the extension or of the tool: it is LibreOffice's, plus the
state the file carries. Where the same text means two functions, the **namespace** decides, and it
is written differently in each format (`docs/FUNCTION_NAMES.md`, generated by
`scripts/function_namespaces.py` from the catalogue of LibreOffice 26.8):

* **LibreOffice does have namespaces of its own.** Its catalogue has `core` functions (no prefix:
  the OpenDocument standard), `microsoft` (`COM.MICROSOFT.`), `openoffice` (`ORG.OPENOFFICE.`),
  `libreoffice` (`ORG.LIBREOFFICE.`: `REGEX`, `COLOR`, `ROUNDSIG`, `FOURIER`…), `legacy` (`LEGACY.`) and the
  analysis add-ins; the number in each is in `docs/FUNCTION_NAMES.md`. An XLSX writes the `microsoft`, `openoffice`
  and `libreoffice` ones with `_xlfn.`.
* The engine registers every function as `namespace::NAME` (`core::SUM`, `microsoft::IFS`) and resolves a call by the
  prefix it carries: in an ODS a bare name is `core`; in an XLSX a name without `_xlfn.` is `core` too, except the
  few that Excel writes bare for a function outside `core` (`CEILING`, `FLOOR`, `FDIST`…, the `XLSX_BARE` table).
  A call that leaves out a prefix the function needs still finds it.
* **Four texts name two functions**, and the namespace tells them apart: `CEILING` and `FLOOR` are
  `core::` in an ODS (the OpenDocument function: signs of number and multiple must agree, `Err:502`
  otherwise; checked by `tests/assets/native.ods`, which LibreOffice created and calculated) and
  `microsoft::` in an XLSX, or as `COM.MICROSOFT.CEILING` in an ODS (Excel's, which LibreOffice calls
  `CEILING.XCL`). `FDIST` and `FINV` are `core::` in an ODS (the ODF function) and `legacy::` in an XLSX
  (the right-tailed one); they are not implemented yet.
* `microsoft::FLOOR(x;0)` is `Err:502` in LibreOffice (Excel: `#DIV/0!`), and Excel's `CEILING`/`FLOOR` need both arguments.
* `EASTERSUNDAY` is bare in an ODS and `_xlfn.ORG.OPENOFFICE.EASTERSUNDAY` in an XLSX: the two formats disagree on
  its namespace, and both resolve to it.

Other Rust spreadsheet engines (IronCalc, GridCraft) are listed in the README as related work; they can be consulted for a doubt about a function, but LibreOffice is the reference.

## Date system (null date)

The date system is a **document setting that LibreOffice stores per document, and any date is allowed**:
the date of serial 0, the *null date*. The default is 1899-12-30; the options of its dialog are 1899-12-30,
1900-01-01 and 1904-01-01, and a file can hold another. The calendar is always the real one: there is no
1900-02-29 (that is Excel's inherited bug, which LibreOffice never applies) and serials before the null date
are negative, down to 0001-01-01. Measured with LibreOffice 26.8, `DATEVALUE("2024-01-01")` is 45292 with null date
1899-12-30, 45290 with 1900-01-01, 43830 with 1904-01-01 and 26863 with 1950-06-15.

| Format | Where the null date lives | What the engine does |
| ------ | ------------------------- | -------------------- |
| ODS | `table:null-date` in `table:calculation-settings` (any date) | uses it, for the date cells it reads and for every function |
| XLSX | `date1904` in `workbookPr`: 1904-01-01 if set | otherwise 1899-12-30, as LibreOffice imports it |
| `sheetc calc`, a model built by hand | none | `--date-system 1899\|1900\|1904\|YYYY-MM-DD`, default 1899 |

Checked by `tests/assets/null_date_{1900,1904,1950}.ods`, created and calculated by LibreOffice
(`scripts/gen_null_date_fixture.py`): `DATE`, `YEAR(0)`, `WEEKDAY`, `TEXT`, `DATEVALUE`, `EDATE`,
`EOMONTH`, `DATEDIF`, `NETWORKDAYS`, `WEEKNUM` and the cached date cells, in each.

## Compatibility features

`enable_features` (`--enable-features`) turns on readings of a formula that LibreOffice 26.8 does
not have. Every feature is off unless the list names it, so the default is the reference's behavior.

- `LONGTEXT`: `_xlfn._LONGTEXT(a, b, …)` with constant text arguments is the text literal of their
  concatenation. LibreOffice 26.2 wrote a literal longer than 255 characters as such a call; 26.8
  evaluates it as `#NAME?`. With the feature on the cell gets the text the writer meant, a deliberate
  difference from the reference, which is why it is opt-in. A call with a non-constant argument stays unknown and is reported,
  with or without the feature.

## Document settings (stored in the file)

Read by `sheetrs-core` as stored (`Workbook::settings`, `None` = not stated) and
resolved into engine options by the loader:

| Setting | XLSX | ODS | Engine |
| ------- | ---- | --- | ------ |
| Iterative calculation | `calcPr iterate/iterateCount/iterateDelta` | `table:iteration status/steps/maximum-difference` | `iteration`, applied when the document switches it on; not overridable. |
| Search criteria: wildcards / regular expressions / literal | — (Excel: wildcards) | `table:use-wildcards`, `table:use-regular-expressions` | `search.mode`. ODF defaults for what the file omits: regular expressions **on**, wildcards off (LibreOffice omits an attribute equal to the default; verified by saving a document with regex on). Wildcards win when both are on. |
| Whole-cell matching | — (Excel: whole cell) | `table:search-criteria-must-apply-to-whole-cell` (default true) | `search.whole_cell`. |
| Case sensitivity | — (Excel: insensitive) | `table:case-sensitive` (default true) | `search.case_sensitive`, **comparison operators only**: with it on, `"a"="A"` is false and `"abc"<"ABD"` is true (letters first, case as tie-break, lowercase first). `COUNTIF`, `MATCH`, `VLOOKUP`, `SEARCH` stay case-insensitive: LibreOffice returns 3 for `COUNTIF(r,"APPLE")` over `apple` cells with the setting on. |
| Two-digit-year window | — | `table:null-year` | `Locale::two_digit_year_start` (default 1930): text dates and LibreOffice `DATE(yy,…)`. |
| Precision as shown | `fullPrecision="0"` | `table:precision-as-shown` | Not applied; the loader adds a diagnostic. |
| Document language | — | default cell style `fo:language`/`fo:country` | Read; informational only (see below). |

Regular expressions are run by LibreOffice with ICU's engine, whose results differ from other
engines' in details (what an empty match is, where `$` and `\b` match, what `.` and `\s` stand
for, how an invalid pattern is treated). The engine reads a subset of ICU's syntax and writes it for
the `regex` engine with ICU's meanings (`sheetrs-engine/src/regex_subset.rs`):

* literals and escaped punctuation, `.` (not a line terminator: `\n`, `\v`, `\f`, `\r`, U+0085,
  U+2028, U+2029), `\d \D \w \W \s \S`, sets (`[a-c]`, `[^x]`, with ranges and `\d \w \s`),
  groups `( )` and `(?: )`, alternation, and `* + ? {n} {n,} {n,m}` with their lazy forms;
* the pattern must not be able to match the empty text, and nothing that repeats may.

What stops the build is anything else: anchors, `\b`, look-around, back-references, options
(`(?i)`), `\p{..}`, the other escapes, set operations, possessive quantifiers, and a pattern that
is not valid. In a criterion the first match must be the whole text (`a|ab` does not match `ab`, as
in LibreOffice), and a text with only `{` or `}` among its special characters is searched as
written. Compared with LibreOffice 26.8 on random patterns of the subset (pattern and
text pairs, `SEARCH` and `COUNTIF`, with and without case): no difference. Case is ignored by the
engine's own folding, which differs from ICU's for letters whose folding is several characters
(`ß` is `ss`, `ﬁ`): a regular expression met with such text stops the build when the build
evaluates it; at run time, with such text in an input, the cell is `#NOT_IMPLEMENTED!`.

An XLSX carries none of the search settings: LibreOffice imports it with wildcards, whole-cell
matching and case-insensitive comparisons, and so does the engine.

### Who decides what

| Decided by | What |
| ---------- | ---- |
| The document | Date system, iteration, search settings (ODS), two-digit-year window. The command line cannot override them. |
| The build configuration (`[locale]`, `--locale`) | Application-wide regional settings that Excel and LibreOffice let the user change outside any document: separators, date order of text dates, month/day names, boolean names, currency, two-digit-year window. Fixed at build time. |
| The run | Only the clock (`NOW()`) and the random seed. |
| Nobody (informational) | The document's language (`fo:language`/`fo:country` of the default cell style). |

The language is not an input to evaluation. Evidence: a probe document
recalculated by LibreOffice with its default style switched to `es-ES` still gave
`TEXT(DATE(2024,3,1),"mmmm dddd")` = `March Friday`, `TRUE&""` = `1`,
`1.5&""` = `1.5`, `DATEVALUE("3/1/2024")` = March 1st and `VALUE("1,5")` = error:
LibreOffice evaluates with the system regional settings, as Excel does, and a
file does not store them. The compiler therefore reports the language as a
diagnostic when it differs from the locale in use, and nothing more.

### Locale support

Five locales are supported: `en-US`, `en-GB`, `es-ES`, `es-CO` and `es-MX` (a bare `en` or `es` is
the first of each). The criterion is fidelity: a locale is in the table only when the engine
reproduces, row by row, what a LibreOffice running with that regional setting computes
(`tests/assets/semantics.*` for `en-US`, `semantics_<tag>.*` for the others, XLSX and ODS), so
the table is not a list of what LibreOffice offers. Any other locale is not supported: a build with
`--locale de-DE` fails.

The `[locale]` table of `sheetc.toml` (and `--locale`) is the user's own regional setting, the
equivalent of what LibreOffice lets a user define globally and per document: it changes any field
of a supported locale, and it defines a region or language the table lacks (`es-BO`, `sw`) from
the separators, names and texts it states. What it states is the user's responsibility; the engine
applies it and does not check it against LibreOffice.

The table (`sheetrs-engine/src/locale_data.rs`) is generated **from LibreOffice**
(`scripts/gen_locale_table.py`), not from a tag or from ICU: a LibreOffice running with the regional
setting gives the separators, the names of months and days (full and abbreviated), the patterns it
accepts for a date typed as text, the order of the short date, the currency format, the texts of
AM, PM, TRUE and FALSE, and the probes of how its scanner reads a date with a month name. **Adding a
locale** means adding its tag to the script *and* its fixture to `scripts/gen_semantics_fixture.py`,
and only keeping it once every row passes. A first attempt with ten more locales (`de`, `fr`, `ja`,
`pt`, `ru`, `sv`, `nl`…) was dropped because the engine could not reproduce them: the letters of a
`TEXT` date code are read in the locale's language and, in some codes, English letters are text
(German `dd.mm.yyyy` gives `dd.03.yyyy`); the order of `a-b-c` dates depends on the first number
in French; the alphabets of Danish, Finnish, Polish or Turkish sort letters after others.

What a locale fixes in the engine: numbers and dates as text (`VALUE`, `DATEVALUE`, arithmetic on
text), `TEXT`/`FIXED`/`DOLLAR` output (separators, names, AM/PM, currency), `&` on numbers, boolean
names, and text order.

**Dates written as text** are read as LibreOffice's scanner reads them, per locale:

* *Digits*: the text must have the shape of one of the locale's patterns (`M/D/Y`, `D/M`, `D-M`…)
  with its separators as written, so `3.1.2024` is not a date in English or Spanish. A pattern
  without a year gives the year of the clock (`3/1` is March 1st of this year: the build's fixed
  `now`, or the clock when the program runs, like `TODAY()`). A year of one or two digits is expanded
  in the window 1930–2029, of three or four is taken as is. `a-b-c` with hyphens is read as
  year-month-day, from any year of digits, after the patterns (`3-1-24` is 2003-01-24 in Spanish).
  A time of day takes the locale's text for AM and PM (`1:30 PM` is not a time in Spanish).
* *Month names*: the word is a full name, an abbreviation, an abbreviation with a dot that is not
  part of it (`mar.`), or `Sept` where the abbreviation is `Sep`; never a prefix, and only the
  locale's language. Weekday names around the date are ignored. What is accepted depends on the form
  written: `Mon D Y`, `D Mon Y`, `Y Mon D`, `Mon D`, `D Mon`, `Mon Y`, `Y Mon`, with a year of two
  digits or four, each with a space, a hyphen or a slash, a dot after the day, a comma
  (`Mar 1, 2024`). The locale's row says, for each form, whether LibreOffice reads it and what the
  lone number of `Mon D` / `D Mon` means (the day of this year, or the year of the first of the
  month: `mar 13` is March 2013 in Spanish). A dotted abbreviation does not stand between two
  numbers with hyphens (`13-mar.-2024`).

**TEXT codes** follow the locale for the names and the separators: `mmm` and `ddd` write the
abbreviations of the table, `/` in a date code the locale's date separator, `AM/PM` the locale's
text, and a language tag in the code (`[$-409]`, `[$-C0A]`, `[$-809]`, `[$-80A]`) the names of that
language. `[$-40A]`, the traditional sort of Spanish, LibreOffice does not know and TEXT keeps the
locale it runs with, as the engine does; a tag that is not a hexadecimal id and has no currency
symbol (`[$-en-US]dddd`, `[$-ZZZ]0`) is `#VALUE!` (LibreOffice's `Err:502`). A `.` in a code that has
no decimal separator of the locale is read as one (`0.0%`). A tag of another language (`[$-407]`)
stops the build when the code is a literal (see *What stops a build*).

Dates reach the year 32767 (`DATE(32767,12,31)` is 11,274,306), as in LibreOffice, and a year of
five digits is read in text (`3/1/12345`).

Text order (`<`, `>`, sorted lookups) is ICU's collation for the language of the locale, as in
LibreOffice (both use ICU; here ICU4X): letters first (`á` sorts with `a`), then accents, then, for
the case-sensitive comparison operators of an ODS document, case, lowercase first. Punctuation,
symbols and currency sort before digits and digits before letters. Every script and emoji are
ordered as there, and so are the alphabets with letters of their own: under `es` the `ñ` is a
letter between `n` and `o` (`"ñu">"nz"` is true), under `en` it is `n` with a tilde. A locale
stated in the configuration is collated by its tag (`sv-SE` as Swedish). It was compared with
LibreOffice 26.8 on 72,771 pairs of strings in seven languages, both strengths, with no difference.
Text is compared as stored (decomposed accents are not recomposed). Excel orders with Windows NLS
tables; not verified against Excel.

The equality of text (`=`, `<>`, `MATCH`, `COUNTIF`, `VLOOKUP`, `SEARCH`…) is not by collation:
ignoring case it compares the uppercase of both texts, as LibreOffice does with its case mapping
(ICU's full mappings with `ß` as `ẞ`, and the final sigma), and with case it compares the characters.
So `ñ` and `n` plus a combining tilde are different, a soft hyphen is not ignored, and
`"straße"="STRASSE"` is false. `UPPER`, `LOWER` and `PROPER` follow the same mapping (`PROPER` as
LibreOffice's code, position by position in UTF-16 units). Compared with LibreOffice 26.8 on equality checks and case mappings: no difference.
Number and date *formatting* is hand-written and tested rather than taken from
CLDR on purpose: CLDR and Excel disagree there (e.g. Spanish does not group
four-digit numbers in CLDR, Excel does).

### Formulas that end in a blank

Scenario: `B1` holds `=A1` and `A1` is empty. Both applications show and store `0`
for `B1` (oracle rows `Data!Z99`, `IF(TRUE,Data!Z99)`, `SUM(Data!Z99,1)`), and the
cell is no longer blank (`ISBLANK(B1)` is false). What differs is the *type* of that
0, which only a comparison or `ISNUMBER` can see:

| | Excel | LibreOffice |
| --- | --- | --- |
| `B1=""` | false | true |
| `B1=0` | true | true |
| `ISNUMBER(B1)` | true | false |
| `B1&"x"` | `0x` | `0x` |
| output / cached value | 0 | 0 |

LibreOffice keeps an *empty result*; the engine reproduces it (checked on 20
oracle rows). The Excel column is its documented behavior and is **not** checked
against Excel; the three rows where the oracle (LibreOffice) differs are listed in
`ORACLE_GAPS` for `semantics.xlsx`. How the cell looks depends on the number format
and the "show zeros" option, which the engine never applies.

### Dates written with a month name

LibreOffice reads `DATEVALUE("…")` and a date typed into a text-to-number coercion with its own input scanner,
which depends on the locale's **date order** and **words**, not on per-locale code. Measured with 26.8 (en-US,
en-GB, es-ES) and reproduced by `parse_named_date` in `sheetrs-engine/src/coerce.rs` from the locale's order and
month and day names (no ICU data is involved):

| Form | space | `-` | `/` |
| ---- | ----- | --- | --- |
| `Mar 1 2024`, `Mar 1 24` (month, day, year) | any order | no | any order |
| `1 Mar 2024` (day, month, year) | day-first locales only (en-GB, es; not en-US) | any order (`1-Mar-2024`) | no |
| `2024-Mar-1` | no (`2024 Mar 1`) | yes | no |
| `Mar 2024` (month, four-digit year) | any order | any order | any order |
| `Mar 1, 2024` (comma after the day) | month-first locales only (en-US) | no | no |

The words are the locale's: `1 marzo 2024` and `mar` are dates under `es` and `March` is not; `March 1 2024` is under
`en` and `marzo` is not. Abbreviations are the first three letters or more, with an optional dot; case and repeated spaces do
not matter; weekday names around the date are ignored; a day that does not exist (`Feb 30 2024`) is an error; `1st` and
`1 de marzo de 2024` are errors. A time may follow. Checked on oracle rows (en and es).

### Errors outside a function's domain

`SQRT(-1)`, `LN(0)`, `ACOSH(0.5)`, `GCD(-1,2)`: Excel reports `#NUM!`. LibreOffice
reports `Err:502`, which the readers translate to `#VALUE!` (and its XLSX export
writes `#VALUE!`), except for a few functions that answer `#NUM!` (`ASIN`, `ACOS`,
`POWER`) or something else. The engine gives LibreOffice's kind, found
with the oracle (`LO_DOMAIN_NUM` and the per-function cases below). The XLSX oracle cannot
check the kind (LibreOffice's export loses it), so it only requires an error where LibreOffice gives one.

### Differences by function

Checked against LibreOffice; the Excel column is Excel's documented
behavior, not checked here.

| Function | Excel | LibreOffice |
| --- | --- | --- |
| `MROUND(5,-2)` | `#NUM!` (signs differ) | rounds anyway (6) |
| `PERCENTRANK(…,5,5)` | truncates to the significance | rounds |
| `BITLSHIFT(1,100)` | `#NUM!` above 53 | 2^100 |
| `EXPONDIST(-1,2,TRUE)` | `#NUM!` | 0 |
| `STANDARDIZE(1,0,0)` | `#NUM!` | `#DIV/0!` |
| `QUOTIENT(1,0)` | `#DIV/0!` | `#VALUE!` |
| `MODE` with no repeats, `PERCENTRANK` out of range, `RANK` over text | `#N/A` | `#VALUE!` |
| `WEEKNUM(DATE(2024,12,31))` | 53 | 1 (a week holding January 1st of the next year is its week 1) |
| `TYPE(TRUE)` | 4 | 1 |
| `TYPE(` a multi-cell range `)` | 64 (a guess: Excel documents 64 for arrays only) | `#VALUE!` |
| `ROMAN(45,TRUE)` | classic | `TRUE` is 1 (form 1) |
| `ARABIC("-IV")` | −4 | `#VALUE!` |

### Hidden rows and nested subtotals

`SUBTOTAL(101…111)` and `AGGREGATE` options 1, 3, 5 and 7 skip hidden rows; the rows
come from the file (`hidden` rows of the sheet). `SUBTOTAL` and `AGGREGATE` options
0–3 skip cells whose own formula holds `SUBTOTAL` or `AGGREGATE`. Both agree with
LibreOffice on oracle rows. Excel also distinguishes filtered rows from manually
hidden ones; the file does not say which, so every hidden row counts as hidden for the
`10x` codes and none for `1`–`11`.

### Case

Function, sheet and defined names are case-insensitive in both applications
(`sum`, `SUM`, `Sheet1`, `sheet1`, `HOJA ñ` = `Hoja Ñ`; compared with Unicode
lowercase). That is unrelated to the **case-sensitive** document setting, which
is about comparing text *values*: Excel has no such setting (`=` is always
case-insensitive; `EXACT` is the case-sensitive test), LibreOffice has one and it
only governs the comparison operators, as described above.

## Cached values read from the files (reader fidelity)

Fidelity also depends on reading what the file stores, not on a convention:

* **ODS dates and times.** An ODS date cell stores an ISO date; the engine needs
  the number the spreadsheet uses, which is the number of days since the
  document's `table:null-date`. `sheetrs-core` used to count from 1899-12-31 (one less
  than the spreadsheet's number from 1900-03-01 on) and read `office:time-value`
  as display text. That is fixed in the `sheetrs-core` reader (same workspace); the
  reader does no further adjustment, and the engine applies the date-system rules
  of the table above to the numbers.
* **Error codes.** LibreOffice stores `Err:5xx` for a family of errors and
  exports several of them as `#VALUE!` to XLSX (`SQRT(-1)`, `LN(0)`, `FACT(171)`
  all become `Err:502`/`#VALUE!`; Excel says `#NUM!`). The engine always
  computes Excel's kind; when comparing with LibreOffice caches only "is an
  error" is checked for those cases.
* **Document settings.** `sheetrs-core` now exposes the calculation settings above (`DocumentSettings`).
* **Typed cached strings.** XLSX formula results typed `str` that look numeric
  (`"005"`) are read by `sheetrs-core` as numbers, and a cached `#VALUE!` of a formula
  that contains `:` is read as no value (`sheetrs` issue #62). The oracle avoids
  those shapes; they only affect *cached* values, which the engine does not use.

## Number and date format codes (`TEXT`, `FIXED`)

LibreOffice reads the format code of `TEXT` **in the user's locale**: `#.##0,00`
under Spanish, where `,` is the decimal separator and `.` groups. The engine
reproduces this (`tests/assets/semantics.*` for English and `semantics_<tag>.*` for four
locales, each formula in XLSX and ODS, computed by LibreOffice 26.8):

* a separator anywhere between digit placeholders turns grouping on; text
  between the decimal placeholders is kept (`#.###.##0` under English gives
  `1234.567.800`);
* the codes LibreOffice reads in English form whatever the locale are a short
  list in `format.rs` (`0.00`, `#,##0`, `#,##0.00`, `0.00%`, `0.00E+00`, the
  `_)` variants). The rule behind it is not known: `#,##0` is `1.235` under
  Spanish while `#,##0;(#,##0)` is `1234,568`. A code outside the list is read in
  the locale;
* sections, conditions (`[>100]`), `[$€-407]` symbols, fractions (`# ??/??`),
  scientific and engineering notation, scaling commas (`0,`), `_)` padding and
  `@`;
* a clock shows what it has reached (`0.999999` is `23:59` in `h:mm`) while
  elapsed time (`[h]:mm`) rounds to the second; `.0` digits round; `A/P`, the
  locale's AM/PM, `NN`/`NNN` and `mmmmm`; negative serials print the real date
  (`1899-12-28`); `[Blue]` after the content is `#VALUE!`.

Not reproduced: a `[$-409]` tag in a non-English locale also changes how `yyyy`
is read (LibreOffice leaves it as text); other language tags do not change the
names (LibreOffice 26.8 ignores them); format codes the oracle matrix does not
cover (`[DBNum1]`, `GG`, `B1`…) are read as literals.

### `_xlfn._longtext`

`=_xlfn._longtext("part 1","part 2")` is not an Excel function. The Delgado
workbook (`docProps/app.xml`: `LibreOffice/26.2.5.2`) holds one, `INPUTS!C17812`: a
help text longer than 255 characters (Excel limits a text literal in a formula to
255), saved as pieces joined by that wrapper, with the whole text as cached value.
LibreOffice 26.8 does not read it back: its full recalculation gives `#NAME?`, and
26.8 does not write it (an ODS → XLSX round trip of a 300-character literal keeps one
literal). Excel's `_xlfn.` prefix marks a *future function*, one the file format does not
define; Excel shows `#NAME?` for one it does not know, and `_longtext` is not defined by Excel. The
error is the right result.

The engine does not implement it, like 26.8: the cell evaluates to `#NAME?` and the
build lists it in the diagnostics (`INPUTS!C17812: \`_xlfn._longtext(…)\` is not an
Excel function…`) and in the unsupported-function warning, so the cell can be
inspected by hand. It is the one formula in 503,867 where `verify --recalc` agrees with
26.8 and `verify` against the cached values differs (the cache holds the text 26.2
computed).

## Behavior the reference fixes

The reference is LibreOffice 26.8 on Linux (a UTF-8 system), not Excel and not LibreOffice on
Windows:

| Case | Behavior |
| ---- | -------- |
| `CHAR`/`CODE` | `CHAR(n)` is the character of code `n` for 0–127 and U+FFFD for 128–255 (the text encoding of a UTF-8 system has no such characters), an error above 255; `CODE` is the first byte of the UTF-8 of the first character (`CODE("€")` is 226), 0 for a character outside the Basic Multilingual Plane and for no text. |
| Booleans in lookups and criteria | They are the numbers 1 and 0: `MATCH(TRUE,{1;2;3},1)` is 1, `COUNTIF(r,TRUE)` counts the 1s. |
| `LET` rebinding a name inside `LET`, `DOLLAR` of a negative as `($1,234.57)`, `FORMULATEXT` in Excel notation, `SECOND(0.7512)`, the digits of a number written as text | Where Excel's documented answer differs from LibreOffice's, the engine gives LibreOffice's. |
| Excel's own `DATEDIF(…,"MD")` result | Pinned to the LibreOffice-verified formula; not checked against Excel. |

### Lookups over an array that is not a range

`MATCH` of type 1 or -1, `LOOKUP`, `VLOOKUP` and `HLOOKUP` over an inline or computed array use code
of their own in LibreOffice (`ScMatch`, `ScLookup`, `CalculateLookup`), which gives other positions
than for a range when the data are not sorted. They follow that code (`functions/matrix_lookup.rs`)
and were compared with LibreOffice 26.8 on 18,000 arrays (numbers, booleans, text, mixed,
duplicates). Also as there: `MATCH` of a type that is not -1, 0 or 1 (after truncating) and of a
two-dimensional range or array is an error, and a square range or array is searched down its first
column. `XLOOKUP` over such an array, in the modes that look for the nearest value (-1, 1) or search
in halves (search modes 2, -2), does the same (4,000 arrays compared), including LibreOffice's own
quirks: the walk down (search mode -1) in those modes skips the last element, and the halving runs
as for descending data when the match mode is 1 or 0. Booleans are numbers in `XLOOKUP` as in
`MATCH`. Match mode 3 (regular expression) is supported.

### Dates outside 0001-01-01 … 32768-01-01

LibreOffice's date functions disagree with each other outside that range (`YEAR` clamps, `TEXT`
gives `#FMT`, `WEEKDAY` errors), so the engine does not imitate them. A formula that handles such a
serial while the build folds it stops the build, naming the cell. A serial that only appears at
run time (an input) gives an error value.

### Parity limits: what is known and what only a run shows

A case the engine does not reproduce is an error when the build can tell it will happen (the data are
constants, or evaluated from constants), so no program is built that differs from LibreOffice. When
it depends on an input the build cannot tell: it compiles with a warning that names the cell, and a
run that meets the case gives the error value `#NOT_IMPLEMENTED!` in that cell (and what depends
on it) instead of a value that would differ. The cases: a `TEXT` code with the language tag of a
language outside the table (`[$-407]`), `XLOOKUP` search modes 2 and -2 over a range (LibreOffice
runs them through an iterator of its own, and the probes of it did not finish), regular
expressions outside the reproduced subset or over text with letters of several-character case
folding, date serials outside 0001-01-01 … 32768-01-01, `F.INV(1, …)` (LibreOffice answers the end of
its search range, 2.37E+81 for 5 and 8 degrees of freedom), and the t, F and beta distributions with
more than 10 million degrees of freedom or shape (see *Distributions* below).

### References that go

A reference that leaves the sheet or is deleted is `#REF!`, and what is written in the file is
what LibreOffice writes:

* A deleted cell or range, in an XLSX: `Sheet!#REF!`; LibreOffice reads it as `#REF!`. A bare
  `#REF!` (what is left of a reference to a removed sheet, and what Excel writes for it) is the
  unknown name `#NAME?` in LibreOffice, **also in an XLSX it saved itself**.
* In an ODS: `[#REF!]` in a formula and `#REF!` as the `table:cell-range-address` of a name.
* A shared formula whose cell would read a column past `XFD` or a row past 1,048,576 (or before
  the first) reads `Sheet!#REF!` for that reference. LibreOffice 26.8 opens such an XLSX with the
  cell as `#REF!` (formula `=#REF!1+1` for a column past `XFD`), not `#NAME?`. The workbook
  builds and the cell is `#REF!` when it runs; the linter reports it as an error cell (ERR102). A
  `Sheet!#REF!` is `#REF!` when the sheet is in the workbook and an unknown name when it is not.
  An ODS has no shared formulas: each cell holds its own formula, and LibreOffice reads a formula
  cell repeated with `table:number-columns-repeated` as one cell, so no reference is moved.
* A 3D reference (`Sheet1:Sheet3!A1`) is not evaluated (#75): it is `#REF!` with a diagnostic, where
  LibreOffice sums, counts and so on across the sheets of the span.
* Tokens that look like a reference past those limits (`XFE1`, `ABCD1`, `A0`, `A1048577`) are names:
  `#NAME?` in a formula, `#REF!` through `INDIRECT`; defined names with those texts are accepted.
  A document has 16,384 columns, 1,048,576 rows and at most 10,000 sheets (what LibreOffice 26.8 accepts, checked by inserting sheets and evaluating references through UNO).

Two behaviors of LibreOffice that the engine and the tools do not copy: its import of an XLSX or
ODS groups neighboring cells that hold one relative formula, and after a deletion the group
moves a range of its own whose first cell is deleted (`SUM(A5:A7)` with rows 4-5 gone) differently
from the same formula in a single cell; the tools give the result of the single cell.

### The C library

`sin`, `cos`, `sinh`, `cosh`, `tanh`, `exp`, `ln` and the other transcendental functions come from the C
library of the machine that runs the executable, as LibreOffice's do. Libraries round some of them
differently in the last bit from one version to the next: `sinh(4)` is `27.289917197127753` in glibc 2.44
and `27.28991719712775` in the oracle. The result of a function that returns a number differs by
that bit (about 1E-16 relative), far below the tolerance the tests compare numbers with (1E-9
relative). The functions that return text with 15 significant digits (`IMSIN`, `IMCOS`, `IMSEC`
and the other `IM` functions) show it in the last digit of a part, up to about 5E-15 relative in the
cases of the oracle, and LibreOffice shows the same on a machine with another C library. The
oracle tests compare the parts of a complex number written as text with a relative tolerance
(`COMPLEX_TEXT_TOLERANCE` in `tests/semantics/common.rs`) and every other text exactly. `ERF` and `ERFC` are the
exception: their algorithm is the one of the C library (see *Distributions*).

## Distributions

The gamma, chi-square, t, F, beta, log-normal, Weibull, hypergeometric and negative binomial
functions, the confidence intervals and the tests built on them (`T.TEST`, `F.TEST`, `CHISQ.TEST`,
`Z.TEST`, `PROB`, `B`) are checked against LibreOffice 26.8 with oracle rows: the values,
the arguments outside the domain (`Err:502`) and the edges (`x` at zero, probabilities at 0 and 1,
degrees of freedom cut to whole numbers, as there).

* **`FDIST` and `FINV` are two functions.** In an ODS the bare names are the OpenDocument ones
  (`F.DIST`, `F.INV`: four and three arguments, left tail); in an XLSX they are the legacy ones
  (right tail, `F.DIST.RT`, `F.INV.RT`). The engine registers both, by namespace.
* **Non-convergence is an error value.** LibreOffice gives up on the series or continued fraction
  of the incomplete gamma function after 10,000 terms (`Err:523`, stored as `#VALUE!`): `GAMMA.DIST`
  and `CHISQ.DIST` with `x` near a shape of 1E7 or more. The engine counts the same terms.
* **Beyond 10 million degrees of freedom the results are not reproduced.** The continued fraction
  of LibreOffice's incomplete beta function loses digits there: `T.DIST(2, 1E8, TRUE)` is off by
  2E-9, `T.DIST(2, 1E9, TRUE)` by 3E-9, `F.DIST(2, 5, 1E9, TRUE)` by 4E-8 and
  `BETA.DIST(0.5, 1E9, 1E9, TRUE)` by 1E-7 from the exact value, and the engine computes the exact
  one. A t, F or beta function over that limit stops the build (`#NOT_IMPLEMENTED!` when the
  value comes from an input).
* `CHIDIST` has no upper limit on the degrees of freedom; `CHISQ.DIST` and `CHISQ.INV` stop at 1E10.

## Dynamic arrays, lookups by text and text splitting

`SEQUENCE`, `FILTER`, `SORT`, `SORTBY`, `TAKE`, `DROP`, `CHOOSECOLS`, `CHOOSEROWS`, `HSTACK`,
`VSTACK`, `EXPAND`, `TOCOL`, `TOROW`, `WRAPROWS`, `WRAPCOLS`, `RANDARRAY`, `XMATCH`, `TEXTSPLIT`,
`TEXTBEFORE`, `TEXTAFTER`, `ENCODEURL` and `ROT13` are checked with oracle rows. What
LibreOffice 26.8 does that the documentation of Excel does not say, and the engine reproduces:

* **Blank cells and errors in an array that came from a range.** `INDEX` of a blank element of
  such an array is the empty text, not a blank. `SORT` of a range gives 0 for an error in it
  (`1, 3, "a", 0` for `1, #N/A, 3, "a"`); the errors sort last. `VSTACK` and `HSTACK` keep them.
  `ROWS` and `COLUMNS` of an error are that error.
* **`FILTER`'s condition** is an error (`Err:504`, `#VALUE!`) for text and for a blank cell, also
  when nothing is selected and `if_empty` is given.
* **A text criterion finds the number it shows, in a range.** `MATCH("5", A1:A8, 0)`,
  `VLOOKUP("5", …, FALSE)`, `HLOOKUP`, `XLOOKUP` (modes 0, 2, 3) and `COUNTIF` find 5, and the
  wildcards (`"*"`, `"?"`) match a number's text too (`MATCH("*", A1:A8, 0)` is 1 over numbers).
  The approximate modes (`MATCH(…, 1)`, `VLOOKUP(…, TRUE)`, `LOOKUP`) and an array constant
  (`MATCH("5", {5;6}, 0)`) do not.
* **`TEXTBEFORE`/`TEXTAFTER` `match_mode`**: any value other than 0 compares without regard to
  case; the delimiters match left to right without overlapping, from the end for a negative
  instance.
* **The names with both prefixes** (`_xlfn._xlws.FILTER`, `_xlfn._xlws.SORT`) are read in an XLSX.

Not reproduced (the build stops, or the cell is `#NOT_IMPLEMENTED!` when the keys are an input):
**`SORTBY`, and `SORT` of an array, by keys that have an error.** The order LibreOffice gives is
not a function of the keys: with `#N/A` in the second of `1, #N/A, 3, "a"` it puts the rows of
`SORTBY` as 1st, ?, ?, 4th ascending and 4th, ?, ?, 3rd descending, and `SORT` of an array keeps the
error where it was.

## Calendar periods, series and sheet information (OpenOffice and LibreOffice extensions)

`WEEKS`, `MONTHS` and `YEARS` (third argument, 0 or 1, required), `ISLEAPYEAR`, `DAYSINMONTH`,
`DAYSINYEAR`, `WEEKSINYEAR`, `ROUNDSIG`, `SERIESSUM`, `RAWSUBTRACT`, `AREAS`, `SHEET`, `SHEETS`,
`HYPERLINK` and `ERRORTYPE` are checked with oracle rows.

* **`WEEKS`, `MONTHS`, `YEARS`**: mode 0 counts complete intervals (`MONTHS` from January 31st to
  February 29th is 0, to March 1st is 1; `YEARS` compares month and day); mode 1 counts the
  boundaries crossed (Mondays, firsts of months, firsts of years). A start after the end gives the
  negative of the swapped count. Weeks start on Monday whatever the locale.
* **`WEEKSINYEAR`** is the ISO week count (53 when the year starts on a Thursday, or ends on one).
* **`SERIESSUM`**: text and blanks in the coefficients count as 0 and keep their place in the
  powers; an error in a range is `Err:504`; at `x = 0` the result is 0 unless the first power is
  `x^0`, which is `#VALUE!`.
* **`RAWSUBTRACT`** is the subtraction without the snap to zero of the `-` operator
  (`0.3 - 0.1 - 0.2` is `-2.8E-17`).
* **`HYPERLINK`** answers the text, or the address without one; a blank is 0 and a boolean a number.
* **`SHEET` and `SHEETS`**: the sheet of a reference, or by name (not case-sensitive; an unknown
  name or anything else is an error). `SHEETS(a, b)` with two references is 2 in LibreOffice and is
  not reproduced (the engine takes one argument).
* **`ERRORTYPE`** answers the internal codes of LibreOffice (532 for `#DIV/0!`, 32767 for
  `#N/A`…), which are not Excel's 1 to 7 (`ERROR.TYPE`). `#VALUE!` has several (502 for an argument
  outside the domain, 519 for the wrong type…) that the engine does not keep apart, so
  `ERRORTYPE` of it stops the build (`#NOT_IMPLEMENTED!` when it comes from an input), and so does
  the error of a cycle.

## Database functions

`DSUM`, `DCOUNT`, `DCOUNTA`, `DAVERAGE`, `DGET`, `DMAX`, `DMIN`, `DPRODUCT`, `DSTDEV`, `DSTDEVP`,
`DVAR` and `DVARP` are checked with oracle rows (every function against 15 criteria blocks
and 16 field arguments, and the arguments that are not a table or a block).

* The field is a name (not case-sensitive; the first column of that name), a position (cut to a
  whole number; `TRUE` is 1) or a cell with either. A position outside the table is `#VALUE!`; a
  name that is not there, `""` and a number as text (`"2"`) are errors.
* The criteria block needs a header row and one row of criteria at least; a header the table lacks
  is an error. The rows of the block are alternatives and the cells of a row all have to hold; an
  empty cell is no condition, and a row of them selects every record. The tests are those of
  `COUNTIF` (`">25"`, `"B*"`, `"="` for blanks, text not case-sensitive).
* `DSUM`, `DMAX`, `DMIN` and `DPRODUCT` over no numbers are 0, `DAVERAGE` is `#DIV/0!`. `DGET` is
  `#VALUE!` for no record and for a record whose field is blank, `Err:502` (`#VALUE!`) for several.
* `DSTDEV` and `DVAR` of no numbers are **0** and of one are `#NUM!`; `DSTDEVP` and `DVARP` of none
  are `#NUM!` and of one are 0.
* **`DCOUNT` and `DCOUNTA` with field 0 are not reproduced**: LibreOffice counts 7 records of the 8
  that match when every criterion is empty (`DCOUNT`) and answers `#VALUE!` for `DCOUNTA` of the
  same, but 2 for both when the criteria select two. The build stops (`#NOT_IMPLEMENTED!` when the
  field comes from an input).

## Regressions, frequencies and modes

`LINEST`, `LOGEST`, `TREND`, `GROWTH`, `FREQUENCY` and `MODE.MULT` are checked with oracle rows (every cell of the answers).

* **Shapes.** `y` is a column or a row; `x` must lie the same way (a column of regressors for a
  column `y`, rows for a row `y`), else `Err:502`. The answer of `LINEST` and `LOGEST` is one row
  of the coefficients (the last regressor first, the intercept last), or five rows with the
  statistics (errors, `r²` and the standard error of `y`, `F` and the degrees of freedom, the sums
  of squares), the cells that do not apply being `#N/A`. `TREND` and `GROWTH` answer the shape of
  `new_x` for one regressor, and one value per row of `new_x` (per column for a row `y`) for several.
* **Data.** Any cell of `y`, `x` or `new_x` that is not a number (text, blank, error) is `Err:502`,
  also for the errors; a scalar error argument is that error. `y` at zero or below is `Err:502` for
  `LOGEST` and `GROWTH`. Fewer points than coefficients is an error; a constant regressor (or one
  that is a combination of the others) is `#VALUE!` for the whole answer.
* **Flags.** `const` and `stats` omitted are `TRUE` and `FALSE`; a number other than 0 and a blank
  cell are `TRUE` and `FALSE`; text that is not a boolean is `FALSE` in `LINEST` and `LOGEST`
  and makes every value of `TREND` and `GROWTH` `#VALUE!`. Without the constant the `r²` and
  `F` are of the uncentered sums of squares and the error of the intercept is `#N/A`.
* **Degrees of freedom zero**: the errors and the standard error are 0 and `F` is `#N/A`.
* **`LOGEST` and `GROWTH`** fit the logarithm and answer the exponential of the coefficients; the
  errors and the other statistics stay in the logarithms.
* **`FREQUENCY`** counts into the bins in the order they are given (a bin of 6 before one of 3 takes
  the values from 3 to 6): text and blanks are ignored, booleans count as numbers, no number in the
  data or in the bins is `#VALUE!` and an error is that error.
* **`MODE.MULT`** answers the values that repeat most, in the order they first appear, as a column;
  without a repeated value it is `#VALUE!` (not Excel's `#N/A`).

Not reproduced (the build stops, `#NOT_IMPLEMENTED!` when the values come from an input):

* **`LINEST` or `LOGEST` with statistics over a perfect fit** that is not exact in the numbers:
  LibreOffice answers the rounding noise of its computation (`F` = 4.3E31 for `LOGEST` of
  1, 2, 4, 8 over 1 to 4, 1.2E+16 for the means of the same logarithms, `#N/A` for the lines it
  computes exactly), which the engine's rounding does not repeat.
* **`FREQUENCY` with equal bins**: which of them takes the count depends on LibreOffice's sort.

## Securities

`COUPPCD`, `COUPNCD`, `COUPNUM`, `COUPDAYBS`, `COUPDAYS`, `COUPDAYSNC`, `PRICE`, `YIELD`, `DURATION`,
`MDURATION`, `DISC`, `PRICEDISC`, `YIELDDISC`, `RECEIVED`, `INTRATE`, `PRICEMAT`, `YIELDMAT`,
`ACCRINT`, `ACCRINTM`, `TBILLPRICE`, `TBILLYIELD` and `TBILLEQ` are checked with oracle rows (pairs of
dates, a grid of pairs around the ends of months, every frequency and basis, and the arguments
outside the domain).

* **The coupon dates** step back from the maturity by whole periods, on the last day of the month
  when the maturity is one. `COUPDAYS` is 360, 365 or the actual days of the period by basis;
  `COUPDAYSNC` is `COUPDAYS - COUPDAYBS` on the 30/360 bases and the actual days otherwise.
* **The day counts differ by function** (LibreOffice computes them in several places that do not
  agree). The engine has each one, found with the oracle:
  * *Coupons, `PRICE`, `DISC`, `YIELDDISC`, `PRICEMAT`, `YIELDMAT`, `DURATION`*: the US 30/360
    count cuts the end day 31 to 30 when the start day, as given, is 30 or 31, and then moves a
    start on the last day of February to 30 (so `COUPDAYBS` from 2023-02-28 to 2023-08-31 is 181,
    not Excel's 180). Basis 1 is `YEARFRAC`'s (the average year of the span).
  * *`PRICEDISC`, `RECEIVED`, `INTRATE`, `ACCRINTM`, `ACCRINT`*: the 30/360 count with no
    adjustment of the days at all (31 stays 31), minus the days February lacks when the dates are
    in one year and the first is in February (2024-02-01 to 2024-08-31 is 209, not 210); on
    basis 1 the days over the days of the year of the *first* date (366 for any span that starts
    in 2024).
  * *`TBILLPRICE`, `TBILLEQ`, `TBILLYIELD`*: 30/360 up to the day after the maturity (`TBILLYIELD`: the
    count to the maturity, plus one). `TBILLEQ` and `TBILLYIELD` are an error above 360 such days;
    `TBILLPRICE` is not limited (and is an error when the fraction is a whole number).
* `ACCRINT` does not use the first interest date and has no calculation-method argument
  (eight arguments are an error); `ACCRINTM` has `par` and `basis` optional.
* `YIELD` is LibreOffice's search (a regula falsi from yields 0 and 1, up to 100 steps), so
  its results agree to the digits it reaches, not to the exact root.
* **Not reproduced**: `TBILLYIELD` with a settlement and a maturity that are both the last day of
  February and less than a year apart (LibreOffice counts 359 or 360 days where its own rule gives
  361). The build stops.

## Depreciation and odd periods

`VDB`, `AMORLINC`, `AMORDEGRC`, `ODDLPRICE` and `ODDLYIELD` are checked with oracle rows.
`ODDFPRICE` and `ODDFYIELD` have no calculation in LibreOffice 26.8.

* **`VDB`** adds the depreciation of every whole period of the life (the declining balance of
  the factor, moving to the straight line of what is left when that is larger, unless `no_switch`)
  in proportion to the part of the period between the start and the end: from 3.5 to 4.2 is half
  of the fourth period and a fifth of the fifth. An empty factor (`VDB(…,,TRUE)`, or a blank
  cell) is 0 and an error; with the argument left out it is 2.
* **`AMORLINC` and `AMORDEGRC`** follow the French system as LibreOffice computes it. The
  period is cut to a whole number; the first period is the fraction of the year (30/360 with the
  rule of the coupon functions) of the rate; the degressive coefficient is 1, 1.5, 2 or 2.5 for
  lives under 3, under 5, up to 6 and longer years, and every amount is rounded to a whole
  number. A negative remainder is 0.
* **`ODDLPRICE` and `ODDLYIELD`** use three fractions of a period (last interest to maturity,
  settlement to maturity, last interest to settlement; `YEARFRAC`-like with the securities'
  30/360), and ask for a rate above 0, a settlement after the last interest, and for the yield
  version a price above 0.
* **`ODDFPRICE` and `ODDFYIELD`** answer `#VALUE!` for every call (LibreOffice has them as
  placeholders), and the engine answers the same.

## Byte functions, `ASC`, `JIS`, `BAHTTEXT` and `REGEX`

`LENB`, `LEFTB`, `RIGHTB`, `MIDB`, `FINDB`, `SEARCHB`, `REPLACEB`, `ASC`, `JIS`, `BAHTTEXT` and `REGEX`
are checked with oracle rows.

* **Bytes** are counted by a table of LibreOffice's, whatever the language of the document:
  one for the characters of `U+0001`–`U+10FF`, `U+1200`–`U+2E7F`, the private use area and a few
  smaller ranges (Latin, Greek, Cyrillic, Thai, symbols, `U+FB00`–`U+FEFF`…), two for the rest
  of the plane (kana, ideographs, Hangul, the full-width **and half-width** forms: `LENB("ｱ")` is 2)
  and two for any character above it (which `LEN` counts as one). The table is generated from
  LibreOffice by `scripts/gen_width_data.py` into `functions/width_data.rs`.
* **A cut through a double-byte character** leaves a space for the byte that is there:
  `LEFTB("日本語", 3)` is `日 `, `MIDB("日本語", 2, 2)` is two spaces. `REPLACEB` is an error when
  the start is past the last byte or the count past the end (`REPLACEB("abc", 4, 1, "x")` too,
  unlike `REPLACE`). `FINDB` and `SEARCHB` count the position in bytes and start at the first
  character that begins at or after the byte given; an empty text to find is `#VALUE!`.
* **`ASC` and `JIS`** convert by tables (full-width letters, digits and punctuation, and the
  katakana, to half-width and back; `JIS` joins a half-width kana with the voiced or semi-voiced
  mark that follows it, and an ideographic space is not changed by `ASC`).
* **`BAHTTEXT`** rounds to the satang (as `ROUND`), reads a hundred and one as `หนึ่งร้อยหนึ่ง`
  (not the `เอ็ด` of the written language) and spells numbers of any size by millions up to
  `1E+300`, from the first fifteen digits.
* **`REGEX`** is case-sensitive and takes the expressions of the reproduced subset, with its
  groups: `$0` to `$9` in the replacement (`$10` is `$1` and a `0`), a backslash for the next
  character (alone at the end it is dropped), and `$` followed by anything else, or a group the
  expression lacks, an error. A fourth argument of `"g"` replaces every match; a number is the
  match to take (0 is the text as it is); no match is `#N/A` (the text unchanged when it
  replaces).

Not reproduced (the build stops, `#NOT_IMPLEMENTED!` when the text comes from an input):

* `LEFTB`, `RIGHTB`, `MIDB` or `REPLACEB` that cut through a character above the plane
  (an emoji): LibreOffice answers half of a surrogate pair, which is not text.
* `REGEX` with an expression outside the subset: one that can match the empty text (`a*`,
  `.*`), anchors, `(?i)`.

## Complex numbers, Bessel functions and `CONVERT`

The `IM*` functions (`COMPLEX`, `IMREAL`, `IMAGINARY`, `IMABS`, `IMARGUMENT`, `IMCONJUGATE`,
`IMSUM`, `IMSUB`, `IMPRODUCT`, `IMDIV`, `IMPOWER`, `IMSQRT`, `IMEXP`, `IMLN`, `IMLOG10`, `IMLOG2`, the
trigonometric and hyperbolic functions and their reciprocals), `BESSELI`, `BESSELJ`, `BESSELK`,
`BESSELY` and `CONVERT` are checked with oracle rows, a seeded random set among them.

* **A complex number is a text** (`3+4i`, `-j`, `1.5e3i`), and a result is written with the first
  15 significant digits (`%.15g`: scientific notation below `1E-4` and from `1E+15`). A unit
  of 1 is written without the number (`i`, `-i`, `1+i`), a zero part is left out, and the result
  of a real number is a plain number in a text. The suffix of the result is the one of the first
  argument that had one (`i` by default); **`IMDIV` takes the suffix of the dividend only**
  (`IMDIV("1","2j")` is `-0.5i`).
* **A number inside the text** is read digit by digit, with the fraction added with a multiplier
  divided by ten each time (`0.0084` is `0.008400000000000001`), so the last digit of a result
  can differ from the one of the number as typed; the engine reads it the same way. A number
  given instead of a text goes through its 15-digit text; a blank is `#VALUE!`.
* **The formulas are LibreOffice's, and the digits follow them**: `IMLN` takes the real part from
  the logarithm of the C library (`log1p` near the unit circle), `IMLOG10` divides by `ln 10` and
  `IMLOG2` multiplies by `1/ln 2`, `IMTAN` is the tangent of the C library (the limit `±i` where
  the hyperbolic functions overflow, a real part that underflows to `0`), `IMSEC`, `IMCSC`,
  `IMCOT`, `IMSECH` and `IMCSCH` divide `1` by those results with the division of the C compiler
  runtime (an infinite divisor gives `0` or `-0`, which is written `-0`), and `IMPOWER` is
  `exp(n log z)`. A sine or cosine with an argument of `2^64` or more, a tangent of `2^63` or
  more, a logarithm of zero, a division by zero and a result that is not finite are `#VALUE!`
  (`Err:502`/`Err:504`).
* **`BESSELI`, `BESSELJ`, `BESSELK` and `BESSELY`** use LibreOffice's algorithms (series for
  `I`, adjoint summation for `J` and `Y`, polynomial approximations for `K`, with the recurrence
  of `K` and `Y` above order 1), so the digits agree with the oracle, not only to the
  precision of the function. The order is truncated (`1.9` is 1, `-0.5` is 0); a negative order
  (after that), `K` or `Y` with `x <= 0`, an order out of the 32-bit range and a result that
  is not finite are `#VALUE!`; a series that does not converge (`J` for large `x` and order,
  `Err:523`) is `#VALUE!` too, and `J` and `Y` take the asymptotic formula above `x = 5E+6`.
* **`CONVERT`** has the table of units of LibreOffice in its order, case-sensitive:
  a unit with a prefix (`k`, `m`, `da`, `u`, `Ki`… of the information units) is looked up
  in the whole table, the last unit that matches wins and an exact name wins over all of them
  (`CONVERT(1,"e","c")` is the erg and the calorie, not a prefix). `m^2` is `m2`, and a prefix
  of a square or cubic unit counts twice or three times (`cm3` is `1E-6 m3`). Units of different
  classes, an unknown unit and an empty one are `#VALUE!`; temperatures go through the base unit
  with their offset, and a binary prefix (`kibit`) is a power of two.

## Names of OpenDocument and LibreOffice: `CHISQDIST`, `CHISQINV`, `WEEKNUM_OOO`, `RAND.NV`

* **`CHISQDIST(x, df[, type])`** is the left tail with the type optional (cumulative by default),
  and **`CHISQINV(p, df)`** the left-tail inverse. Unlike `CHISQ.DIST` and `CHISQ.INV` they take
  any `df` (cut to a whole number, at least 1) and give 0 for a negative `x`. The density is
  LibreOffice's: a logarithm form for `df * x` above 1,391,000, the product of the terms otherwise.
* **`WEEKNUM_OOO(date, type)`** (`_xlfn.ORG.LIBREOFFICE.WEEKNUM_OOO` in a file) takes the type
  required, starts the week on Sunday for type 1 and on Monday for **any other number**
  (`WEEKNUM_OOO(d, 0)` is not an error), and the week 1 is the one with at least 4 days in the year, so
  it differs from `WEEKNUM` (`WEEKNUM_OOO(DATE(2021,1,1), 1)` is 53, `WEEKNUM` gives 1).
* **`RAND.NV()` and `RANDBETWEEN.NV(min, max)`** are `RAND` and `RANDBETWEEN` that LibreOffice does
  not recalculate; a program computes each cell once, so they are the same. **Both limits of
  `RANDBETWEEN` go to the next whole number away from zero, then they are compared**
  (`RANDBETWEEN(1.2, 1.9)` is 2, `RANDBETWEEN(2.5, 2.4)` is 3; the engine used to answer `#VALUE!`
  for both).
* **No file can use** `EFFECT_ADD`, `NOMINAL_ADD`, `CUMIPMT_ADD`, `CUMPRINC_ADD`, `ISEVEN_ADD`,
  `ISODD_ADD`, `GCD_EXCEL2003`, `LCM_EXCEL2003`, `WEEKNUM_EXCEL2003`, `NETWORKDAYS_EXCEL2003` and
  `CONVERT_OOO`: LibreOffice lists them, but a formula that names them is `#NAME?` in an OpenDocument
  file (ODF names), in an XLSX file with or without `_xlfn.` and `_xlfn.ORG.LIBREOFFICE.`, and in its own
  grammar (checked with `soffice` 26.8). They are not counted as functions to implement.

## `FOURIER`, option pricing, `COLOR`, `CURRENT` and `EUROCONVERT`

`FOURIER`, the four `OPT_*` functions, `COLOR`, `CURRENT` and `EUROCONVERT` are checked with
oracle rows (random series and options among them).

* **`FOURIER(series, by_column[, inverse][, polar][, min_magnitude])`** has LibreOffice's transforms
  (radix-2 with its twiddle factors, Bluestein's for other lengths, a packed one for real input of
  even length), so the digits are its own. Real input is one column (or row), complex input two
  (the real and imaginary parts); the result has two columns. The grouping, as a text, is a
  number or `TRUE`/`FALSE` (anything else is `#VALUE!`), the other flags are read leniently (a
  text that is not a number is 0). A series with a blank, a text or an error among its cells is
  `#VALUE!`; more than two columns (by column) or rows (by rows) is `#VALUE!`; **an error in
  an argument is the result, the leftmost first**.
* **`FOURIER` by rows of an array written in the formula** is a defect of LibreOffice that is not
  reproduced: it transposes the matrix in place, which for such an array is the formula's own, so
  each calculation flips it (a file saved after a calculation holds the transposed array, and
  the cached value comes from the original). The build stops, naming it. A range and a computed
  array (`TRANSPOSE({…})`) are not affected, nor is a series by column.
* **`OPT_BARRIER`, `OPT_TOUCH`, `OPT_PROB_HIT` and `OPT_PROB_INMONEY`** (the pricing add-in:
  an ODS names them `COM.SUN.STAR.SHEET.ADDIN.PRICINGFUNCTIONS.GETOPT…`, an XLSX by their own
  name) price barrier and touch options in the Black-Scholes model with their greeks, as
  `black_scholes.cxx` does. The texts are case-sensitive and by their first letter (`call` or
  `put`; `in` or `out`; `cont` or `end`; `for` or `dom`; the greek `value`, `price`, `delta`,
  `gamma`, `theta`, `vega`, `volga`, `vanna`, `rho`, `rhof` or their initials), a missing put or call is a
  call, a missing greek the value, a missing strike of `OPT_PROB_INMONEY` is no strike; a number
  or a bool where a text goes is `#VALUE!`, as is a non-positive spot or volatility, a negative
  time (or strike) and a result that is not finite.
* **`COLOR(red, green, blue[, alpha])`** (`_xlfn.ORG.LIBREOFFICE.COLOR`) is
  `alpha*2^24 + red*65536 + green*256 + blue` of the arguments cut to a whole number, each in
  0…255. **`CURRENT()`** is always `#VALUE!` (`Err:518`): it needs the value of the cell that a
  conditional format is computing. **`EUROCONVERT(value, from, to[, full_precision[, precision]])`**
  converts through the euro with the fixed rates of the euro and the currencies LibreOffice knows (names
  without case), rounds the result to the decimals of the currency unless `full_precision`
  and rounds the intermediate amount to `precision` (at least 3) digits.
* **An error in an argument comes before an argument out of its limits, the leftmost error
  first** (`COLOR(300, NA(), 1/0)` is `#N/A`); this is the rule of `COLOR`, `EUROCONVERT` and
  `FOURIER`.
* **`ERF` and `ERFC`** (and the normal distribution functions through them) use the algorithm of
  the C library: the same bits as glibc 2.39 gives (the previous series and
  continued fraction differed in the last digit for some arguments).

## Exponential smoothing: `FORECAST.ETS`

`FORECAST.ETS` (ODS: `FORECAST.ETS.ADD`), `FORECAST.ETS.MULT`, `FORECAST.ETS.CONFINT`
(`FORECAST.ETS.PI.ADD`), `FORECAST.ETS.PI.MULT`, `FORECAST.ETS.STAT` (`FORECAST.ETS.STAT.ADD`),
`FORECAST.ETS.STAT.MULT` and `FORECAST.ETS.SEASONALITY` are checked with oracle rows
(random series with trend and seasons, month and day timelines, gaps, repeated and unsorted
values, every aggregation, the argument errors).

* **The method is LibreOffice's** (`ScETSForecastCalculation`): Holt-Winters additive or
  multiplicative, with the smoothing constants found by bisection on the mean squared error (to a
  resolution of 0.001, each constant inside the previous one), Kahan sums, the length of the
  period found by comparing the differences a period apart when the seasonality is 1 (and a
  length of 1 meaning no season), and the first complete periods for the initial seasonal values.
  A target inside the timeline answers the **data value** of that step, not the smoothed one
  (interpolated with the next forecast from 0.001 of a step on).
* **Timelines**: a timeline whose values fall on the same day of the month is a step of months
  (the values become `12 year + month`, a target is converted with the length of its month);
  otherwise the step is the smallest difference, and a gap that is a multiple of it is filled
  (half of the average of its neighbours with data completion, 0 without) up to 30% of the points,
  more is `#VALUE!`. A repeated value is aggregated as the argument says (1 average is the first
  value, as LibreOffice does, not the average; 7 sum; 2 and 3 count; 4 max; 5 median; 6 min; 0
  is `#VALUE!`). The sort is libstdc++'s `std::sort`, whose order of equal values matters
  for the average.
* **Arguments**: the seasonality is a whole number (0 none, 1 automatic, else the length), anything
  else is `#NUM!`; completion 0 or 1; aggregation 1 to 7; the confidence level 0 to 1; the statistic
  type 1 to 9 (alpha, gamma, beta, MASE, SMAPE, MAE, RMSE, step, period); a target before the
  start of the timeline (before its end, for the interval) is `#NUM!`; sizes that differ or a non-number
  in the values or the timeline are `#VALUE!`; fewer than two periods with seasons is `#VALUE!`. An
  error in an argument is the result, the leftmost first. A result that is not finite is `#NUM!`.
* **The prediction interval** is computed for the double smoothing (seasonality 0) from the
  normal quantile; it is not for the others (below).

Not reproduced (the build stops, `#NOT_IMPLEMENTED!` when the series comes from an input):

* **`FORECAST.ETS.CONFINT` and `FORECAST.ETS.PI.MULT` with seasons** (any seasonality but 0):
  LibreOffice computes the interval from 1000 random scenarios, so its answer changes with each
  calculation (and for some series it crashes).
* **A prediction interval for a target that is not on a step** (`CONFINT(4.5, …)` after a last value
  of 4, a month timeline) reads past the end of a vector in LibreOffice: its answer is whatever is
  in that memory.
* A timeline that its sort would handle by heap sort (never seen).

## `CELL`, `INFO` and `STYLE`

Checked with oracle rows.

* **`CELL(type[, reference])`**: `ADDRESS` is `$B$3`, with the sheet when it is not the one of the
  formula (`Data!$B$3` for a document that came from XLSX, `$Data.$B$3` from ODS; a range or a whole
  row or column is its first cell); `COL`, `ROW` and `SHEET` (from 1) of the first cell; `COORD`
  is `$A:$B$3` (the sheet's letters, then the cell); `CONTENTS` the value (0 for an empty cell,
  the error of a cell that holds one) and `TYPE` `b` for an empty cell, `l` for text and `v` for
  anything else. Without a reference the cell is the formula's: `CELL("contents")` is a circular
  reference (`Err:522`, `#VALUE!` in a file) and `CELL("type")` is `v`. The type is read without
  case and whole (`"addres"` is `Err:502`); **a second argument that is not a reference is `#REF!`
  before the type is looked at** (`CELL("x", 1)`), an error in it is the result.
* **`INFO(type)`**: `recalc` is `Automatic`, `numfile` is 1, and `directory`, `origin`, `memavail`,
  `totmem` and `memused` are `#N/A` (LibreOffice's `directory` too); any other text is `Err:502`.
  `recalc` is always `Automatic`: a program recalculates what its inputs change, so a document in manual
  calculation mode (LibreOffice answers `Manual`) is computed as if automatic; the manual mode is not
  honored (it would keep stale values and every cached value in the program). **The build warns** when the
  document is in manual mode (XLSX `calcMode="manual"`, ODS `AutoCalculate` false in `settings.xml`); the
  program itself runs without warnings.
  `system` is `LINUX`, `WNT` or `MACOSX`, `osversion` is `Linux 6.18` (major and minor of the kernel;
  `Windows (32-bit) NT 5.01` elsewhere, as LibreOffice) and `release` the build id of the LibreOffice
  that is reproduced: **they are those of the machine the program runs on, as `NOW` is the clock's,
  unless fixed** with `--system`, `--osversion`, `--release` (or `[host]` in `sheetc.toml`) when
  the program is built, or the same options when it runs (the run wins), for results that do not
  change from one machine to another (CI). `INFO` cells are never folded at build time.
* **`CELL("filename")`** is `file:///dir/[book.xlsx]Sheet` for a document that came from XLSX and
  `'file:///dir/book.ods'#$Sheet` from ODS (the sheet of the reference), as LibreOffice writes it. The
  file name is the workbook's (`--filename` fixes another) and the directory the one of the
  executable (`--directory` fixes it), percent-encoded as a URL. Those cells are kept out of
  build-time folding.
* **`STYLE(style[, seconds[, style]])`** applies a cell style and gives 0, whether the style exists or
  not; the time must be a number (`#VALUE!` otherwise). The style is not applied: the output of a
  program is the values.

Not reproduced (the build stops, `#NOT_IMPLEMENTED!` when the text comes from an input):

* `CELL` with `color`, `format`, `parentheses`, `prefix`, `protect` or `width`: they depend
  on the cell's format, its alignment and protection and the column width, which the
  compiler does not keep; and `CELL("address")` of a sheet whose name needs quotes.
