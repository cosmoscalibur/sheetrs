# Approved differences from LibreOffice

SheetRS gives the result LibreOffice gives. A difference exists only if the maintainer approved it,
and it is recorded here with where it is described. Anything else that differs is a bug or a pending
decision, never a documented feature.

**What "the result LibreOffice gives" means.** It is what LibreOffice shows when the workbook is saved and
opened again (re-read), in both formats and for every operation. The state of its memory right after an edit is
not a reference: the same workbook, saved and opened by someone else, shows other values, so it is a defect of
LibreOffice and a result that only the memory gives is not a difference of SheetRS (see `CONTRIBUTING.md`, *Parity and
fidelity*). The evidence of each entry below is a re-read.

| Difference | Where | Why |
| ---------- | ----- | --- |
| A query has no direction (rows or columns): the cells come in the order of the sheet | `sheetrs-query/README.md` | Scope of the tool |
| Some mathematical functions are computed with `libm` and may differ in the last digits from LibreOffice's | `sheetrs-compiler/docs/FIDELITY.md` | Technical |
| `LONGTEXT` (the pieces of a text over 255 characters) is a feature that is enabled on request | `sheetrs-compiler/README.md` | Scope |
| `include_formulas` is `false` by default in a query: a search by value looks at what was typed, not at the results of formulas | `sheetrs-query/README.md` | Usability |
| A cached error of an XLSX is read as the file keeps it (`#VALUE!`), where LibreOffice recalculates the cells with an error when it opens the file and shows its own code (`Err:502`, `Err:522`). To have LibreOffice's errors, recalculate the workbook first (see the recipe) and read the result | `sheetrs-query/README.md`, `docs/recipes.md` | Reading does not calculate |
| Regular expressions outside the subset of ICU that was compared with LibreOffice are refused in a search and in a replacement, instead of giving another result (issue #82 extends the subset). The anchors `^` and `$` are in the subset of a search (`find`, `sheetrs query --find`) and of a replacement (`replace`, `sheetrs edit --replace`), as LibreOffice reads them in a cell (compared in both formats); they stay outside the subset of the functions of the engine (`REGEX`, `COUNTIF`...), whose semantics are another matter. A pattern that can match the empty text (`x*`, `^`, `$`, `a*$`, `(^|$)`) is read by both, as `findAll` and `replaceAll` read it (compared in both formats); the empty search text matches nothing in both, as in LibreOffice (no error, nothing read). What stays refused is listed in `sheetrs-query/README.md` | `sheetrs-query/README.md`, `sheetrs-edit/README.md` | Scope |
| Only the three date systems of the LibreOffice Calc interface are supported: 1899-12-30 (the default, and the 1900 system of an XLSX), 1900-01-01 (StarCalc 1.0) and 1904-01-01. LibreOffice can store another null date (its API, a crafted ODS `table:null-date`); SheetRS gives an error that names the date, when the workbook is read, in every tool, instead of numbering the dates from it | `sheetrs-compiler/docs/FIDELITY.md` (Date system), `sheetrs-io` (`Error::UnsupportedDateSystem`) | Scope: an arbitrary null date is not reachable from the interface and no tool writes it |
| `FORECAST.ETS` and its variants, with an error written in an option or next to a series of a single value: LibreOffice reads the error as a number (the payload of the NaN) and uses it without checking it (`FORECAST.ETS(7,{1;3;2;5;4;6},{1;2;3;4;5;6},#NAME?)` is 9.22337203685478E+18, the largest 64-bit integer), SheetRS answers the error | `sheetrs-compiler/docs/FIDELITY.md` | An unchecked conversion of LibreOffice, not a rule; the error is the useful answer |
| Only the A1 notation of references is supported. LibreOffice can read and show references in R1C1 notation (*Tools ▸ Options ▸ Calc ▸ Formula*, and in the API); SheetRS has no R1C1 grammar: a range written in R1C1 (`T!R1C1:R2C2`) is refused in every tool with "is not a range", and the formulas of a file are always read in the notation the format stores (A1) | `docs/coding-patterns.md` (Formula Normalization) | Scope: R1C1 is not usual and no file stores it |
| A cell that depends on what the engine cannot calculate and that the run calculates (an edit reaches it, or every formula is calculated), where the result is one only LibreOffice gives: `WEBSERVICE` (the response of a server, `Err:540` offline), `FILTERXML` and `DDE`, is an error that names the cause, never another value (a workbook with macros is refused by the build, below, unless secure mode). What LibreOffice keeps, SheetRS keeps (no option): a cell no edit reaches keeps the result the file caches, a reference to another workbook keeps the stored value of the link, and the report holds a warning of its kind (`EXTERNAL_FROM_CACHE`, `MACRO_FROM_CACHE`, `EXTENSION_FROM_CACHE`); an add-in that is not installed is `#NAME?` when calculated, as in LibreOffice (OBSERVED, 26.8, both formats) | `sheetrs-compiler/docs/FIDELITY.md` (*What depends on what the engine cannot calculate*), `sheetrs-edit/README.md`, `sheetrs-edit/tests/from_cache.rs` | The engine cannot run a macro, call a server or an XML engine, so the result of a calculated cell is not the engine's; the cache is the result of a cell nothing calculates |
| A replacement by a regular expression that skipped an empty match before a character outside the Basic Multilingual Plane and can then match half of it (`^|.` on a cell with an emoji): LibreOffice writes a text with a lone surrogate (not valid in UTF-16 text as a character, and not representable in UTF-8 or in XML; it brought a LibreOffice server down in the probe); SheetRS goes on after the whole character | `sheetrs-edit/README.md` | The result of LibreOffice is not a valid text: a Rust `String` and the XML of both formats cannot hold it |

Adding a line requires the maintainer's approval, in the pull request or the issue it came from.

## Proposed, not approved

These differences from LibreOffice exist in the code and wait for the maintainer's decision; nothing
here is approved until it moves to the table above.

| Difference | Where | Why it is proposed |
| ---------- | ----- | ------------------ |
| `de-DE`: the keywords of a format code are read in English (`dd.mm.yyyy`, `[Red]`, `[$-409]dddd d`), where a German LibreOffice reads `TT.MM.JJJJ` and `[ROT]` and keeps `d`, `y`, `[Red]` as text or an error (`dd.mm.yyyy` is `dd.03.yyyy`, a code with `[Red]` is `Err:502`). 19 rows of `semantics_de-DE.*` | `sheetrs-compiler/docs/FIDELITY.md` (Locale support), `sheetrs-compiler/tests/semantics/oracle.rs` (`GERMAN_FORMAT_CODES`) | Needs the table of keywords of each locale (`FormatElementsKeywords`), which the engine does not have; the separators, names and dates of `de-DE` match |
| In the default mode (the cache) the formulas calculated and the ones that keep what the file caches are those of `LibreOffice` re-read, in both formats (`write_to_libreoffice.rs` runs the default mode now, for every fixture of the oracle, against what `LibreOffice` shows; `FIDELITY.md`, *What LibreOffice calculates on load* and *What a deletion reaches*). What is not reproduced, each with the experiment that shows the reason: (1) `CELL("width")`, `CELL("format")`, `CELL("color")`, `CELL("prefix")`, `CELL("protect")` and `CELL("parentheses")` depend on the width of the column, the format, the alignment and the protection of the cell (`probe_cell_format.py`: the same formula over the same cell gives another result when only one of those changes); the model of the engine holds none of them (the readers hand over the number format only), so the engine answers an error and `LibreOffice`'s values are not given; (2) a formula that reads another workbook, calls a macro or calls a function the engine lacks keeps the result the file caches where `LibreOffice` calculates it on load (an ODS number with no format, `DDE`: `#N/A`; an ODS with a `Basic/` library: `#MACRO?` for a name it takes for a macro, by the macro security of the installation) and where an edit reaches a formula that mixes another workbook with local cells (`LibreOffice` calculates it from the stored value: `A1+D1` is 48 after `D1` goes from 5 to 6; the parser does not read the reference, so the dependency walk cannot see the local cells of the formula); the engine cannot calculate what depends on them (`probe.py` of `from_cache`, `FIDELITY.md`); (3) the formulas that `LibreOffice` groups (adjacent formulas of a column with the same relative references) are found in the cell above and below with the same text of references; the rules were probed on the shapes of `probe_hide_groups.py` and `probe_ods_recalculation.py` (a number style that is not General is told by the elements of the style probed there: `number:number` with or without `number:decimal-places`, `number:min-integer-digits`, grouping, text around it, scientific, percentage, currency, date, time, boolean, text), and a repeated row of formulas of an ODS was not probed (the file did not load) | `sheetrs-edit/tests/write_to_libreoffice.rs` (`the_default_mode_gives_the_values_libreoffice_shows_on_open`, the default mode run now against `reread_default`; `the_default_mode_matches_libreoffice_but_for_approved_differences`, the files the oracle recorded), `sheetrs-edit/tests/assets/write_to/oracle.json`, `probe_dirty.py`, `probe_ods_recalculation.py`, `probe_hide_groups.py`, `probe_cell_format.py` | (1) needs the alignment, protection and width of the cells in the model; (2) the engine cannot reproduce them, so there is no result to give; (3) as written |
| In an ODS, deleting the rows of the anchor of the shape of `structure/book.ods` that ends two rows below it (`T!1:2`, `T!1:3`: 3 of the 190 bands of `shapes_delete.json`): the file LibreOffice saves, opened again, gives the shape the height 297 (hundredths of a millimeter); its memory has 1200 and 748, which is what SheetRS places and the file of `sheetrs edit` gives when LibreOffice opens it (`compare_structure_with_libreoffice.py`, `delete rows T!1:2`). In an XLSX the re-read sizes are one to three hundredths of a millimeter smaller than the memory (the sizes go through EMU when LibreOffice saves and loads), within the tolerance of the test, and the end-to-end comparison of the XLSX is the same | `sheetrs-io/src/write/shapes.rs` (`NOT_THE_REREAD`), `sheetrs-io/tests/assets/oracle/shapes_delete.json` | The file of LibreOffice holds an end cell and offsets that its memory does not agree with; reproducing the height it saves needs the logic of its ODS export of an anchored shape, which has not been studied (the cause is unverified) |
| An XLSX input that holds a qualified error (`COUNT(Data!#REF!)`, the form Excel writes for a reference to a deleted sheet or deleted cells of another sheet) and a run that deletes nothing (a hide, a replacement, a calculation): the values are the re-read ones (`COUNT` 0, `COUNTA` 1, `IFERROR` caught: SheetRS reads the error as a whole), but the text of the untouched formula stays `COUNT(Data!#REF!)`, where the file LibreOffice saves holds `COUNT(#REF!)`. If LibreOffice hard-recalculates SheetRS's file (`calculateAll`) it reads the qualified form as a reference with no cell and gives `COUNT` `#REF!`, `COUNTA` `#REF!`, `IFERROR` `#REF!` where its own file gives 0, 1 and 0 (the default load shows the cached values, equal except `SUM`, which LibreOffice recalculates on load: `#REF!` where the cache says `#NAME?`). A run that deletes rows, columns or sheets rewrites the formula and writes the bare error | `sheetrs-edit/tests/write_to_libreoffice.rs` (`the_file_reads_in_libreoffice_as_the_one_libreoffice_saves`), `oracle.json` (`preref`, the edits "(no deletion)") | Writing the text bare needs every formula of every sheet scanned in every pass (measured: +0.25 s, 3.6 %, on 2.4 M formulas for the cheapest scan, a byte search of the inflated sheets; not kept). Open question for the maintainer: rewrite the text only in the cells a run touches |
| A workbook that carries macros is refused by the build itself (`sheetrs_compiler::compile`, `Error::Macros`), where `LibreOffice` opens it, keeps the cached results of what no edit reaches, and runs the macros or shows `#MACRO?` by its security level. The refusal belongs to the build, so every tool that builds has it, in every layer and with no policy of the layer: `sheetc build`, `calculate` and `evaluate`, `sheetrs edit` (the runs that run the engine: a conversion of an XLSX whose cached results are right builds nothing and does not refuse), the Rust, Python and WebAssembly `Book`, and the libraries; the error names secure mode. `inspect` and `verify` only read the workbook and do not refuse it. With secure mode (`--secure-mode`, `secure_mode = true`, `Book::with_secure_mode`, `secure_mode=True`, `secureMode`) the workbook is opened instead: a call to a macro (a function no spreadsheet program has, in a workbook with macros) that the run calculates is an error cell, `Err:531` (`#MACRO?`, an XLSX holds `#VALUE!`), where `LibreOffice` gives `#MACRO?` or the macro's value; what no edit reaches keeps the cache with `MACRO_FROM_CACHE`; the run warns (`UNSUPPORTED_AS_ERROR`). The same mode makes a call to `WEBSERVICE`, `FILTERXML` or `DDE` that the run calculates an error cell and a warning (`Err:540`, `#NOT_IMPLEMENTED!`, `#N/A`), where `LibreOffice` shows the response of a server (`Err:540` offline), a value (`7`) or `#N/A`, and by default stops with an error that names the cause | `sheetrs-compiler/README.md` (*Secure mode*), `sheetrs-compiler/docs/FIDELITY.md`, `sheetrs-compiler/src/compile.rs` (`compile`, `settle_found`, `unsupported_error`), `sheetrs-compiler/tests/macros.rs`, `sheetrs-edit/tests/from_cache.rs` | Technical reason: the engine does not run macros, so the cell that calls one has no result it can give, and LibreOffice's own is the macro's value or a `#MACRO?` that depends on the security level of the installation (not in the file); a build that went on silently would write values that differ from what the same workbook shows in LibreOffice. Refusing by default, in the build, is the maintainer's decision for every layer, and secure mode is the opt-in to go on with an error cell and a warning where `LibreOffice` shows a value or runs the macro; whether either stays is for the maintainer |
| A conversion of an XLSX that keeps the cache and whose results are right converts the results the file caches with no engine, so the report holds no `EXTERNAL_FROM_CACHE`, `MACRO_FROM_CACHE` or `EXTENSION_FROM_CACHE` warning there (it holds one wherever the engine runs, and always for an ODS) | `sheetrs-edit/README.md`, `sheetrs-edit/tests/from_cache.rs` | The kinds are found while the compiler reads the formulas; an engine run for a warning costs the read the short path avoids (6.4 s on 2.4 M formulas against the compile of a calculation, `docs/performance.md`) |
| The numbers a writer writes keep all their digits (the shortest decimal that reads back to the same double: `0.3333333333333333`, `0.30000000000000004`, `9007199254740992`), where `LibreOffice` writes 15 significant digits (`0.333333333333333`, `0.3`, `9007199254740990`; an ODS in scientific form from 1E+15). `LibreOffice` shows the same text for both; the value differs after the 15th digit. It shows in a result the engine calculates (a conversion with `calculate_all`, a recalculation, every ODS) and in a constant, not in the default mode of an XLSX, which converts the 15 digits the file caches (probed with `writer_results.rs`, both formats, both date systems: `fraction`, `float sum 0.1+0.2`, `2^53+1`, `date and time`) | `sheetrs-io/README.md` (*What the writers change of a result when they write it*), `sheetrs-edit/tests/writer_results.rs` | Technical: the file holds the value the engine calculated, not a rounding of it; reproducing the rounding means emulating how `LibreOffice` formats a double (15 digits, scientific from 1E+15 in an ODS and not in an XLSX) and would make the file hold a value other than the calculated one. Parity would be to round: the maintainer decides |
| An XLSX constant that is infinite is written `inf` / `-inf` (`NaN` as `NaN`), where `LibreOffice` writes `INF` / `-INF` and reads `inf` as 0. In an ODS `LibreOffice` writes 0 for NaN and the infinities and the writers write `NaN` / `inf` / `-inf`, which `LibreOffice` reads as 0: the same result, another file. The engine gives no infinity (an overflow is `#NUM!`); only a constant given to `CellWrites::constant` can be one | `sheetrs-io/README.md` (*What the writers change...*), `sheetrs-edit/tests/writer_results.rs` | Nothing technical: `INF` is what `LibreOffice` spells, and neither spelling is a number in the file format; the maintainer decides between the spelling of `LibreOffice` (parity) and refusing a non-finite constant |
| `Constant::Text("")` in an ODS is a string cell with an empty paragraph, where `LibreOffice` leaves an empty cell for an empty text typed or set (and for a formula that gives `""`, which is a string cell, `LibreOffice` keeps the same). `LibreOffice` shows a text cell for the first and an empty cell for its own file (an XLSX is the same: a blank cell in both) | `sheetrs-io/README.md` (*What the writers change...*), `sheetrs-edit/tests/writer_results.rs` | Nothing technical; the writer keeps the text of the request as the text it was given, and parity would be `Constant::Empty` for the empty text |
| A constant text that `LibreOffice` would read as a number or a formula when typed (a leading `=`, `1`, `TRUE`) is a text cell with the format the cell had (General), where the API of `LibreOffice` marks the cell with the text format `@`. The text and the type are the same after the file is opened | `sheetrs-io/README.md` (*What the writers change...*), `sheetrs-edit/tests/writer_results.rs` | Nothing technical: a constant has no format, the cell keeps its own; the mark `@` is what its API adds and not something the file needs |
| The form in which a value is written differs, and `LibreOffice` shows the same for both: an XLSX text is an inline string where `LibreOffice` writes shared strings; very large and very small numbers are the plain decimal expansion of the double (`1E+300` is 301 characters, `5E-324` is 326) where `LibreOffice` writes `1E+300`; in an ODS a date, a time, a percentage and a currency are `float` with the style that carries the format, where `LibreOffice` writes `date`, `time`, `percentage` and `currency` values (`office:date-value`, `office:currency`), so a program that reads `office:value-type` and not the style sees a number | `sheetrs-io/README.md` (*What the writers change...*), `sheetrs-edit/tests/writer_results.rs` | The writers copy the cell element and its style, and write the value in the type the cell has; the inline string avoids rebuilding the table of shared strings in a stream. None changes what `LibreOffice` shows (`differences_*` of the oracle holds none of these cells) |
